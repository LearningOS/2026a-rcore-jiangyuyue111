# Lab 5：并发同步与死锁检测

## 实验目标

本实验在第八章线程模型、互斥锁、信号量和条件变量的基础上加入资源分配记账与死锁检测。检测开启后，内核在真正修改同步对象之前判断请求是否仍处于安全状态；不安全请求返回 `-0xDEAD`，避免线程进入无法继续推进的循环等待。

## 检测器设计

每个进程分别维护互斥锁检测器和信号量检测器，避免两类资源的编号和数量互相干扰。检测器记录三类状态：

- `available`：每一种同步资源当前可分配的数量；
- `allocation[tid][resource]`：各线程已经持有的资源数量；
- `need[tid]`：线程当前正在请求的一份资源。

创建互斥锁时注册一个初始数量为 1 的资源；创建信号量时以许可数作为初始数量。线程退出并回收 TID 时同步清除其检测记录，防止后续复用相同 TID 时继承旧状态。

## 安全性判断

`is_safe` 使用银行家算法式的模拟，但只针对本实验模型中的“每个线程至多有一个当前请求”。算法复制一份 `available`，然后反复寻找能够完成的线程：没有待处理请求的线程可以直接完成；有请求的线程仅在对应模拟资源数量大于 0 时可以完成。线程完成后，把它原先持有的全部资源归还到模拟资源池。

若一轮扫描没有任何线程能够完成且仍有未完成线程，则当前分配状态不安全。安全性判断只读真实状态，模拟过程不会改变同步对象、阻塞队列或调度状态。

## 互斥锁记账

系统调用在进入互斥锁实现前调用 `Resource::request`。如果请求安全，锁实现把当前线程标记为等待者；立即取得锁时调用 `acquire`。阻塞互斥锁释放时，所有权在唤醒队首线程之前完成转移，保证资源记账与锁的实际持有者始终一致。自旋式互斥锁在每次让出处理器前释放内部借用，重新运行后再次检查锁状态。

条件变量等待会先释放互斥锁，收到通知后再重新取得同一把锁。重新加锁路径同样更新资源状态，因此条件变量不会绕过互斥锁记账。

## 信号量记账

`down` 在修改计数器前检查请求。请求被拒绝时不减少计数、不加入等待队列；请求通过后只减少一次计数。若许可可立即取得，则为当前线程登记分配；否则线程进入 FIFO 等待队列并阻塞。

`up` 先归还调用线程的一份资源，再增加信号量计数。仍有等待者时，内核把许可直接登记给队首线程，然后唤醒它；被唤醒的线程从原来的 `down` 继续执行，不重复扣减计数或登记分配。这一顺序使信号量计数、等待队列和检测器三者保持一致，也支持由未持有许可的线程执行事件通知。

## 接口行为

`enable_deadlock_detect` 只接受 0 或 1。开启检测前，内核先检查当前状态是否安全；不安全时拒绝切换。关闭检测只停止拒绝请求，资源分配和释放仍持续记账，因此之后重新开启时能够基于完整状态判断。

## 调试与验证

验证在 WSL2 Ubuntu 中进行。互斥锁用例构造两线程、两把锁的循环等待，内核成功拒绝最后一个不安全请求。信号量用例分别覆盖必然形成循环等待的分配，以及虽然资源暂时耗尽、但仍存在安全完成顺序的分配。

```text
make -C ci-user test CHAPTER=8
```

测评还回归运行线程创建与等待、管道、文件、条件变量、生产者消费者、哲学家就餐及自旋锁计数等基础用例。由于测评给 QEMU 的运行窗口为 30 秒，在 Windows 挂载盘直接运行可能因文件系统开销提前超时；把工作副本放到 WSL 的 Linux 文件系统后可以稳定完成全部用例。

## 实验总结

死锁检测不能只维护一张抽象表，它必须与同步原语的真实状态转换保持原子一致：请求要先检查再入队，释放与所有权转移要在唤醒之前完成。把检测器封装成同步对象共享的 `Resource` 后，互斥锁和信号量可以复用同一套安全性算法，同时各自保留正确的阻塞与唤醒语义。
